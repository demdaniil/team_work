🔢 Предварительная оценка
  • ·Оценка проводится без чёткой привязки к владельцу зоны
  • ·Представители направления (DEV + QA) участвуют в оценке всех задач
Цель
  • ·Представители всех направлений участвуют в предварительной оценке
  • ·По мере роста экспертизы внутри направлений — точность оценки по своей зоне возрастает, голос направления становится весомее
📋 Планирование задач
  • ·Есть первые шаги по специализации команд — но без привязки к направлениям
  • ·Задачи распределяются в первую очередь по специализации
  • ·Остальное — по остаточному принципу
  • ·Появляется одно направление — задачи в его зоне идут туда
  • ·Декомпозиты от направления (подзадачи не входящие в зону ответственности направления) — уходят в пул остального департамента
  • ·Всё вне границ направления — остаётся в департаменте как прежде
Цель
  • ·Задача идёт в направление по степени изменений и бизнес-составляющей
  • ·Декомпозиты (задачи не входящие в зону направления) явно распределяются между направлениями по ownership
📥 Регистратура
  • ·Предварительная проработка задачи централизована
  • ·Нет чёткого исполнителя — зависит от доступности
  • ·Контекст теряется при передаче между командами
  • ·Процесс регистратуры не меняется
  • ·Команды в регистратуре имеют право обратиться за консультацией к тех лидам направления
Цель
  • ·Команда регистратуры собирается из представителей всех направлений
  • ·При необходимости задача разбирается глубже с конкретным направлением
🏗️ Архитектурное согласование
  • ·Централизованное согласование — узкое место
  • ·Нет чёткого разделения кто за что отвечает архитектурно
  • ·Тех лид направления согласует решения внутри своей зоны
  • ·Всё что выходит за границу — согласуется с департаментом по существующим регламентам согласования (они не меняются)
Цель
  • ·Каждое направление имеет одного или нескольких тех лидов — точку входа для технических вопросов
  • ·Общая архитектура согласуется между тех лидами направлений — финальным согласователем выступает доменный архитектор
  • ·Изменения контрактов — явное согласование между сторонами
👁️ Код ревью
  • ·Есть эксперты по сервисам которые проводят ревью
  • ·Эксперты находятся в разных командах — есть риск потери контекста между собой
  • ·Ревью по кодовой базе направления — внутри его команды
  • ·Сопряжённые зоны с департаментом — ревью совместно
Цель
  • ·Ревью полностью внутри направления по своей кодовой базе
  • ·Ревью в сопряжённых зонах с участием соседнего направления — до момента отделения сопряжённой зоны в отдельный модуль/сервис
🔗 Интеграционное тестирование
  • ·Выборочно, для крупных задач/проектов
  • ·Нет закреплённой ответственности — делается ситуативно
  • ·Направление берёт ответственность за тестирование своих интеграций
  • ·Интеграции с зонами департамента — совместно
Цель
  • ·Ответственность за интеграционное тестирование закреплена за направлением
  • ·Явный процесс согласования при тестировании стыков между направлениями
🧪 Регресс
  • ·Кейсы раскиданы между исполнителями разных команд
  • ·Регресс в зоне направления — за командой направления
  • ·Остальные кейсы остаются в департаменте
Цель
  • ·Регресс своей зоны — полностью ответственность направления
  • ·Покрытие и актуальность кейсов контролируется внутри
🚀 CI/CD
  • ·Есть релиз-инженеры и эксперты сервисов, отвечающие за релиз задач
  • ·Ответственность за релиз размыта между людьми в разных командах
  • ·Направление берёт на себя релиз всех сервисов попавших в него
  • ·Планирование релизов смежных областей — совместно с департаментом
Цель
  • ·Направление полностью несёт ответственность за релиз своих сервисов
  • ·Планирование и координация релизов смежных зон — через синк с другими направлениями
🚨 Дежурство
  • ·Общее дежурство без привязки к кодовой базе
  • ·Дежурный может не знать контекст проблемного сервиса
  • ·Дежурство остаётся как прежде
  • ·Дежурная команда может запросить помощь направления если проблема попадает в его зону
Цель
  • ·Дежурная команда собирается из представителей всех направлений — для выявления проблем по всей кодовой базе. При необходимости проблема разбирается совместно с конкретным направлением
  • ·Разбор инцидентов на тест и бою — ответственность направления
  • ·Кодовая база закреплена — ответственность за стабильность тоже
🛠️ Технический бэклог
  • ·Технические эпики заводятся без привязки к чему-то объединённому
  • ·Чаще всего в рамках конкретного сервиса
  • ·Нет общей картины технического долга по зонам
  • ·Работа с техническим бэклогом в целом не меняется
  • ·Направление должно иметь возможность видеть свой технический бэклог — задачи относящиеся к его зоне ответственности
Цель
  • ·Каждое направление имеет свой технический бэклог
  • ·Направление само отстаивает свой технический долг
  • ·Прозрачная картина технического состояния по каждому направлению
