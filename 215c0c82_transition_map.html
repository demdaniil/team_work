🔢 Предварительная оценка
  • ·Оценка проводится без чёткой привязки к владельцу зоны
  • ·Представители субдомена (Техлиды: Аналитика/Разработка/Тестирование) участвуют в оценке всех задач
Цель
  • ·Представители всех субдоменов участвуют в предварительной оценке
  • ·По мере роста экспертизы внутри субдоменов - точность оценки по своей зоне возрастает, голос субдомена становится весомее
📋 Планирование задач
  • ·Есть первые шаги по специализации команд - но без привязки к субдоменам
  • ·Задачи распределяются в первую очередь по специализации
  • ·Остальное - по остаточному принципу
  • ·Появляется один субдомен - задачи в его зоне идут туда
  • ·Декомпозиты от субдомена (подзадачи не входящие в зону ответственности субдомена) - уходят в пул остального департамента
  • ·Всё вне границ субдомена - остаётся в департаменте как прежде
Цель
  • ·Задача идёт в субдомен по степени изменений и бизнес-составляющей
  • ·Декомпозиты (задачи не входящие в зону субдомена) явно распределяются между субдоменами по ownership
📥 Регистратура
  • ·Предварительная проработка задачи централизована
  • ·Нет чёткого исполнителя - зависит от доступности
  • ·Контекст теряется при передаче между командами
  • ·Процесс регистратуры не меняется
  • ·Команды в регистратуре имеют право обратиться за консультацией к тех лидам субдомена
Цель
  • ·Команда регистратуры собирается из представителей всех субдоменов
  • ·При необходимости задача разбирается глубже с конкретным субдоменом
🏗️ Архитектурное согласование
  • ·Централизованное согласование - узкое место
  • ·Нет чёткого разделения кто за что отвечает архитектурно
  • ·Тех лид субдомена согласует решения внутри своей зоны
  • ·Всё что выходит за границу - согласуется с департаментом по существующим регламентам согласования (они не меняются)
Цель
  • ·Каждый субдомен имеет одного или нескольких тех лидов - точку входа для технических вопросов
  • ·Общая архитектура согласуется между тех лидами субдоменов - финальным согласователем выступает доменный архитектор
  • ·Изменения контрактов - явное согласование между сторонами
👁️ Код ревью
  • ·Есть эксперты по сервисам которые проводят ревью
  • ·Эксперты находятся в разных командах - есть риск потери контекста между собой
  • ·Ревью по кодовой базе субдомена - внутри его команды
  • ·Сопряжённые зоны с департаментом - ревью по существующим регламентам
Цель
  • ·Ревью полностью внутри субдомена по своей кодовой базе
  • ·Ревью в сопряжённых зонах с участием соседнего субдомена - до момента отделения сопряжённой зоны в отдельный модуль/сервис в случае если модуль не крупного сервиса. Если смежный сервис ключевой - ревью становится ответственностью двух субдоменов
  • ·*Желаемый конечный результат - полная автономность внутри субдомена
🔗 Интеграционное тестирование
  • ·Выборочно, для крупных задач/проектов
  • ·Нет закреплённой ответственности - делается ситуативно
  • ·Субдомен берёт ответственность за тестирование своих интеграций
  • ·Интеграции с зонами департамента - совместно
Цель
  • ·Ответственность за интеграционное тестирование закреплена за субдоменом
  • ·Явный процесс согласования при тестировании стыков между субдоменами
🚀 CI/CD
  • ·Есть релиз-инженеры и эксперты сервисов, отвечающие за релиз задач
  • ·Ответственность за релиз размыта между людьми в разных командах
  • ·Субдомен берёт на себя релиз всех сервисов попавших в него
  • ·Планирование релизов смежных областей - совместно с департаментом
Цель
  • ·Субдомен полностью несёт ответственность за релиз своих сервисов
  • ·Планирование и координация релизов смежных зон - через синк с другими субдоменами
🚨 Дежурство
  • ·Общее дежурство без привязки к кодовой базе
  • ·Дежурный может не знать контекст проблемного сервиса
  • ·Дежурство остаётся как прежде
  • ·Дежурная команда может запросить помощь субдомена если проблема попадает в его зону
Цель
  • ·Дежурная команда собирается из представителей всех субдоменов - для выявления проблем по всей кодовой базе. При необходимости проблема разбирается совместно с конкретным субдоменом
  • ·Разбор инцидентов на тест и бою - ответственность субдомена
  • ·Кодовая база закреплена - ответственность за стабильность тоже
🛠️ Технический бэклог
  • ·Технические эпики заводятся без привязки к чему-то объединённому
  • ·Чаще всего в рамках конкретного сервиса
  • ·Нет общей картины технического долга по зонам
  • ·При запуске субдомена - начинаем формировать технический бэклог
  • ·В параллель определяем процентное соотношение технической квоты
Цель
  • ·Каждый субдомен имеет свой технический бэклог и квоту на его выполнение
  • ·Субдомен сам отстаивает свой технический долг
  • ·Прозрачная картина технического состояния по каждому субдомену
