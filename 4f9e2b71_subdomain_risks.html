Неравномерное распределение бэклога
Ситуация когда бизнесовые задачи концентрируются в одном субдомене при простое других
⚠ Риск
🗂️
Разделение кодовой базы на core и non-core
На этапе запуска субдомена - превентивно разделить кодовую базу на ядро (core) и периферию (non-core). При перегрузе внешним командам по возможности отдаются только non-core задачи.
  • →Core - ключевая логика, критические сервисы, высокая цена ошибки
  • →Non-core - изолированные модули, утилиты, задачи с явными границами. При перегрузе - передаются командам извне субдомена
  • →Деление пересматривается по мере роста субдомена
★ Делать превентивно, до первого перегруза
🔍
Усиленный refinement при перегрузе
При высокой нагрузке тех лиды усиливают своё присутствие на refinement - совместно с внутренними и внешними командами. Цель: итерация пусть и тяжёлая, но не разъедется по контексту между участниками.
  • →В штатной ситуации - тех лид(ы) могут делегировать разбор задач своим командам или проводить его верхнеуровнево без деталей
  • →При перегрузе - тех лид(ы) ответственно участвуют в refinement с обеими сторонами
  • →Особенно критично если в итерации участвуют внешние команды
2
Другой департамент берёт задачи из нашего бэклога
⚠ Риск
📊
Собрать статистику и оформить как субдомен
Пока запускается первый субдомен - собрать статистику за год: сколько команд и участников из другого департамента брали задачи из нашей зоны. На основе данных - прикинуть человеко-ресурсы и рассмотреть запуск для них отдельного субдомена.
  • →Устойчивый поток задач = фактически уже сложившийся ownership, который стоит легализовать
★ Делать параллельно с запуском первого субдомена
📋
ADR как обязательное условие
Задача не считается завершённой без ADR если в процессе было принято архитектурное решение. Страховка на случай когда команда ушла, а вопросы остались.
  • →ADR фиксирует не только решение но и контекст почему именно так
  • →Шаблон ADR предоставляет субдомен - чтобы формат был единым
🎬
Периодические демо
Регулярные демо для тех лидов субдомена - не для галочки, а как точка явного контроля. Момент когда видно что сделано и как, пока отклонения ещё не зарылись глубоко в кодовую базу.
  • →Демо - обязательное условие, не опциональное
  • →По результатам тех лид субдомена может вернуть задачу на доработку
🔁
Явный онбординг и офбординг
Каждая ротация внешней команды проходит по явному протоколу. Без него каждый приход - потеря контекста, каждый уход - потеря знания.
  • →Онбординг - сессия с тех лидом субдомена: контекст зоны, стандарты, что нельзя трогать
  • →Офбординг - явная передача: что сделано, что осталось, где документация
🔍
Обязательное ревью тех лидом субдомена
Финальную приёмку кода проводит тех лид(ы) субдомена - не опционально. Задача закрывается только после явного approve. Это не замедляет процесс, это исключает накопление скрытого долга.
  • →Ревью - условие закрытия задачи, фиксируется в definition of done
  • →При разногласиях - решающее слово за тех лидом субдомена
